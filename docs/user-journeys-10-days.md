# จำลองผู้ใช้ 10 คน × 10 วัน

ทดสอบบน `codex/ai-signal-research` โดยใช้บัญชี เซสชัน เวิร์กสเปซ
บทสนทนา และเซตอัปแยกกันใน PostgreSQL schema ชั่วคราว ผ่าน API จริง
และ Harness จริง ใช้ Responses provider กับข้อมูลตลาดจำลองในเครื่อง
ไม่มีค่าโมเดล ไม่มีการส่งคำสั่งซื้อขายหรือแจ้งเตือนภายนอก

## วิธีจำลองเวลา

มี 10 รอบวันเรียงลำดับ แต่ละรอบผู้ใช้ 10 คนทำงานพร้อมกัน
การกระทำภายในบัญชีเรียงตามลำดับ เก็บข้อมูลข้ามรอบในฐานข้อมูลเดิม
เริ่ม application instance ใหม่ระหว่างวันเพื่อทดสอบการคืนข้อมูลหลังรีสตาร์ต
โดยไม่ลดเพดานคำขอจริงเพื่อให้เทสผ่าน

นี่คือการจำลอง 100 วันผู้ใช้แบบเร่งเวลา ไม่ใช่เปิดระบบทิ้งไว้ 240 ชั่วโมง
และไม่ได้เลื่อนนาฬิกาตลาดหรือรันทุกรอบของ worker ตลอดสิบวัน
กรณีหมดอายุทดสอบโดยตั้งเวลาหมดอายุของข้อมูล fixture ให้ผ่านขอบเขตจริง

## รูปแบบผู้ใช้

| คน | สไตล์ | สถานการณ์สำคัญ |
|---|---|---|
| 1 | มือใหม่ | ถามก่อนมีร่าง บันทึกจากแชท กลับมาแก้ทุกวัน เซสชันหมดอายุวันที่ 6 และครบโควตา Free วันที่ 10 |
| 2 | รอบคอบ | วันคี่เก็บร่าง วันคู่บันทึก ตรวจว่ารุ่นเดิมยังแจ้งเตือนขณะร่างใหม่ค้าง |
| 3 | Short ระยะสั้น | ใช้ Futures Short 15m ตรวจทิศทางและรักษาตัวตนเซตอัปข้าม revision |
| 4 | สองฝั่ง | Long/Short แยกเงื่อนไข บันทึกและเปิดใช้งานทุกวัน |
| 5 | Break & Retest | รอทดสอบระดับและยืนยัน เพิ่ม ATR วันที่ 2 แชร์วันที่ 3 ตรวจ snapshot ไม่เปลี่ยนและยกเลิกแชร์วันที่ 7 |
| 6 | ขั้นสูง | ครบ 6 เงื่อนไข AND/OR/HOLD บน 5 กรอบเวลา Short แบบ mirror และ ATR; Pro หมดอายุวันที่ 9 แล้วต่ออายุวันที่ 10 |
| 7 | แก้เอง | ปรับ spec และบันทึกผ่าน API โดยไม่มี AI call ตรวจ ledger เป็นศูนย์ |
| 8 | หลายเวิร์กสเปซ | สลับพื้นที่ทุกวัน ปฏิเสธการอ่าน/บันทึก/เปิด/หยุดข้ามพื้นที่ ลบพื้นที่รองวันที่ 8 และตรวจย้ายข้อมูลกลับ |
| 9 | หลายแท็บ/ใจร้อน | ร่างเก่าพยายามทับ กดบันทึกพร้อมกัน 3 ครั้งทุกวัน และส่งซ้ำระหว่างคำตอบช้าวันที่ 4 |
| 10 | ระบบล้มเหลว | สลับ provider 500 กับ incomplete ทุกวัน แล้วลองใหม่ ตรวจคืนโควตาครบ 10 ครั้ง |

ทุกวันตรวจสิทธิ์ข้ามบัญชี ความคงอยู่ของร่าง/เวอร์ชัน ประวัติ การ์ดล่าสุด
การบันทึกซ้ำ การเปิด/พัก และไม่มี RUNNING/RESERVED ค้าง
จบสิบวันตรวจว่ามีเซตอัปคนละหนึ่งรายการและ revision ต่อเนื่องไม่มีช่องว่าง
ตรวจ rate limit แยก: 180 คำขอผ่าน คำขอถัดไปได้ 429 และบัญชีอื่นยังใช้งานได้

## บั๊กที่พบและแก้

1. **เปิด/หยุดเซตอัปข้ามเวิร์กสเปซได้:** เส้นทาง activation ตรวจเจ้าของและ revision
   แต่ไม่ได้ตรวจ workspace จึงหยุดเซตอัปที่ซ่อนจากพื้นที่ปัจจุบันได้
   เพิ่มเงื่อนไข workspace ทั้งก่อนตรวจตลาดและใน transaction
   เคสจำลองล้มเหลวก่อนแก้ (ได้ 200 แทน 409) และผ่านหลังแก้ทั้งเปิดกับหยุด
2. **ข้อความ rate limit ไม่ตรง UX:** ได้รหัส `INTERNAL` กับข้อความอังกฤษ
   เพิ่ม `RATE_LIMITED` และข้อความไทยพร้อมจำนวนวินาทีที่ต้องรอ
   คงเพดาน 180 ครั้งต่อนาทีและ Retry-After เดิม

พบข้อจำกัดเครื่องมือทดสอบด้วย: integration scripts ใช้ local PostgreSQL ร่วมกัน
เมื่อรันพร้อมกัน script ที่เริ่มฐานข้อมูลอาจปิดมันก่อนอีก script จบ
จึงรันชุด integration ตามลำดับ; ไม่ตีความข้อผิดพลาดนี้เป็นบั๊กของผลิตภัณฑ์

```powershell
npm test
npm run typecheck
npm run test:integration
npm run test:chat-save
npm run test:harness
```

ผลรอบสุดท้าย: 100 วันผู้ใช้, 1,861 authenticated API requests และ

รัน journeys ซ้ำหลังแก้บั๊กแล้วผ่าน; unit tests 394/394, typecheck,
general integration, chat-save, Harness contracts และ signal-insight integration ผ่าน
