# SNAAP — การจำลองผู้ใช้ 10 แบบ ตลอด 14 วัน

วันที่ตรวจ: 4 ตุลาคม 2026

## จุดประสงค์

ทดสอบงานหลัก: อธิบายไอเดีย → ออกแบบเทรดเซตอัป → ตรวจบนกราฟ → ยืนยันเปิดติดตาม → รับและทบทวนสัญญาณ → ปรับเซตอัปต่อ โดยไม่ส่งคำสั่งซื้อขายแทนผู้ใช้

## วิธีและขอบเขต

- ผู้ใช้แบบสคริปต์ 10 แบบ × 14 วันเสมือน × ข้อมูลตลาดสังเคราะห์ 3 ชุด = 420 วัน-ผู้ใช้ หรือ 30 เส้นทางการใช้งาน
- เรียก API จริง 1,506 ครั้ง และตัว monitor จริง 852 ครั้ง ใช้ PostgreSQL ฐานข้อมูลชั่วคราวแยกจากข้อมูลผู้ใช้ ลบทิ้งหลังทดสอบ
- สร้างแท่งราคา 15m และรวมเป็น 1h/4h/1d ประเมินแบบรับข้อมูลสะสมรายวัน แล้วเรียกซ้ำเพื่อทดสอบ checkpoint/deduplication
- หยุดทุกเซตอัปในวันที่ 8 กลับมาเปิดวันที่ 9; บางคนเจอข้อมูลขัดข้องวันที่ 7; ผู้ชอบทดลองแก้วันที่ 5 และ 10 พร้อมจำลองแท็บเก่า; ผู้ใช้ Pro หมดสิทธิ์วันที่ 11
- เวลาแท่งราคา/การเปิดเซตอัป/ข้อความเป็น fixture เสมือน การหมดสิทธิ์จำลองด้วยการเปลี่ยน entitlement ในฐานข้อมูลทดสอบ ไม่ได้เปลี่ยนนาฬิกาเซิร์ฟเวอร์ทั้งระบบ
- ข้อความแชตเป็น fixture ไม่ใช่คำตอบจาก AI; ไม่มีการส่ง Telegram/LINE/Webhook จริง ไม่มีการรอ 14 วันจริง ไม่ใช่การทดสอบ soak หรือความสามารถรับโหลด
- ไม่จำลองคนจริงด้วยการอ้างความพอใจ ข้อเสนอ UX ด้านล่างเป็นสมมติฐานจากงานที่แต่ละคนต้องทำ ต้องให้ผู้ใช้จริงยืนยันอีกครั้ง
- ใช้ engine/API/monitor จริง แต่ไม่ได้วัดการลากกราฟ คลิกมือถือ หรือคุณภาพการอ่านภาพ/สนทนา AI ในการรันนี้
- รันซ้ำทั้งชุดอีกครั้งเพื่อยืนยันผล ได้จำนวนสัญญาณและผลตรวจเหมือนเดิม รายงานนับเฉพาะชุดสุดท้าย ไม่บวกสองชุดเป็นการทดลองอิสระ

สคริปต์: `scripts/simulate-personas.ts` — รันด้วย `npx tsx scripts/simulate-personas.ts`
ผลดิบและประวัติรายวัน: `.local/reports/persona-simulation.json`

## ผลที่ยืนยันด้วยการรัน

ตรวจทั้งหมด 204 จุด: ผ่าน 151 ไม่ผ่าน 53 จุด ตัวเลขไม่ผ่านเป็นการเกิดซ้ำของปัญหา 4 กลุ่ม ไม่ใช่บั๊กใหม่ 53 ตัว และไม่ใช่อัตราความสำเร็จของผู้ใช้จริง

### 1. Pro หมดอายุแล้ว monitor หยุด แต่สถานะเซตอัปยังเปิด — สำคัญที่สุด

พบ 3/3 รอบของผู้ใช้หลายเซตอัป วันที่ 11 ไม่มี checkpoint เดินต่อ ทั้งที่ `active=true` และเปิดอยู่ 4 รายการ หลังสิทธิ์เหลือ Free ซึ่งเปิดได้ 3 รายการ

`src/monitor.ts` ข้ามการตรวจหากจำนวน active เกินสิทธิ์ ทั้งใน scan และ evaluateTarget จึงกระทบทุกเซตอัปของบัญชี ไม่ใช่แค่รายการเกินโควตา

ควรแจ้งล่วงหน้าและให้ผู้ใช้เลือกที่จะเปิดต่อ; ถ้ายังไม่เลือกต้องแสดงสถานะ “ต้องเลือกเซตอัปเพื่อเริ่มติดตามต่อ” ชัดเจน ห้ามปล่อยให้ดูเหมือนกำลังติดตามอยู่ หากจะมีค่าเริ่มต้นว่าจะพักรายการใดต้องตกลงพฤติกรรมกับผู้ใช้ ไม่เลือกแทนอย่างเงียบๆ

### 2. ประวัติสัญญาณในหน้าหลักตันที่ 100 รายการ

พบ 20/30 เส้นทาง API คืนสูงสุด 100 รายการ ไม่มี cursor ใน `/api/v1/signals` รายการที่เก่ากว่ายังเก็บในฐานข้อมูล และมี export แต่การเลื่อนทบทวนในหน้าประวัติหลักไม่ครบ

ควรมี pagination, ช่วงวันที่, กรองเซตอัป/ประเภทเหตุการณ์ และลิงก์เปิดกราฟพร้อมเวอร์ชันที่สร้างสัญญาณนั้น

### 3. ขอหลักฐานสัปดาห์แรกแล้วบริบทไม่ครบ

พบ 27/30 เส้นทาง ขณะที่อีก 3 เส้นทางมีสัญญาณน้อยหรือไม่มีสัญญาณ `contextBundle` เลือก 20 รายการล่าสุดก่อนกรองเวลา จึงตัดหลักฐานเก่าทิ้ง

เกณฑ์ทดสอบนี้เปรียบเทียบจำนวนหลักฐานที่ตรงช่วงเวลากับที่คืนมา ไม่ได้หมายความว่าต้องส่งทุกสัญญาณเข้า AI ควรกรองช่วงเวลาก่อน ค่อยเลือกข้อมูลที่เกี่ยวข้อง พร้อมแจ้งจำนวนทั้งหมด/ที่เลือก/ส่วนที่ยังไม่ดึง และเครื่องมือขอเพิ่ม

### 4. คุยครบสองสัปดาห์แล้วข้อความล่าสุดหายจากการโหลด

พบ 3/3 รอบของผู้คุยละเอียด ข้อความ 224 รายการ แต่ API โหลด 200 รายการแรก ทำให้ข้อความวันที่ 14 ไม่ปรากฏ ข้อมูลไม่ได้ถูกลบ

ควรโหลดจากข้อความล่าสุด แล้วค่อยย้อนโหลดข้อความเก่า โดยไม่เปลี่ยนคำตอบ AI เก่าให้กลายเป็นข้อเท็จจริงส่วนบุคคล

- ส่งการแก้ไขจาก revision เก่าถูกปฏิเสธทั้งสองครั้ง: 3/3 เส้นทางของผู้ชอบทดลอง

ผลเหล่านี้ตรวจเฉพาะเงื่อนไขที่ระบุ ไม่ได้พิสูจน์ว่าตัวคำนวณทุก indicator ถูกต้องหรือการส่งข้อความปลายทางสำเร็จ

## สิ่งที่ควรเพิ่มให้ตรงงานหลัก (ข้อเสนอ ไม่ใช่ผลสัมภาษณ์)

1. **สถานะเซตอัปอ่านแล้วรู้ทันที:** ร่าง / กำลังตรวจ / รอขั้นที่ 2 / อยู่ในวงจรสัญญาณ / พัก / ข้อมูลขาด / ต้องจัดการสิทธิ์ พร้อมเวลาตรวจสำเร็จล่าสุด
2. **ทุกแจ้งเตือนตอบได้ว่าเกิดเพราะอะไร:** คู่ กระดาน ตลาด กรอบเวลา ค่า indicator ที่ใช้ เงื่อนไขที่ผ่าน เวอร์ชัน และปุ่มเปิดกราฟ ณ แท่งนั้น
3. **ออกแบบร่างโดยไม่ทำของเดิมหยุดเงียบๆ:** ปัจจุบัน save จะพักเซตอัปซึ่งปลอดภัยด้านการเปลี่ยนเงื่อนไข แต่คนปรับบ่อยเสี่ยงลืมเปิดใหม่ ควรคงเวอร์ชันที่ยืนยันแล้วและให้ร่างอยู่แยก จนกดสลับพร้อมจัดการวงจรเก่าอย่างชัดเจน
4. **ก่อนเปิดมีการทดลองที่เข้าใจง่าย:** จำนวนเหตุการณ์ในช่วงข้อมูลที่มี, เวลาและ coverage, ตัวอย่างผ่าน/รอ/หมดอายุ/ยกเลิก ไม่ตีความจำนวนสัญญาณเป็นความแม่นยำหรือกำไร
5. **ผู้ใช้เลือกเหตุการณ์ที่จะส่ง:** ENTRY/EXIT เป็นหลัก ส่วนหมดอายุ/ยกเลิกเลือกได้ว่าจะส่งทันทีหรือเก็บไว้ในเว็บ ในชุดรอสองขั้นมี EXPIRED 71–121 ครั้ง การส่งทุกเหตุการณ์อาจรบกวน แต่เป็นสมมติฐาน UX ที่ต้องทดสอบ
6. **ปุ่ม “ทำไมยังไม่แจ้ง?”:** แสดงค่าที่ประเมินจริง เงื่อนไขที่ยังรอและสุขภาพข้อมูล เพราะการไม่มีสัญญาณอาจถูกต้องตามเซตอัป ไม่ใช่บั๊ก
7. **ช่วยเริ่มจากเป้าหมาย:** เลือกกระดาน/คู่ → บอกสิ่งที่รอ → เห็นภาพ → ปรับรายละเอียด ไม่ให้คนเริ่มจากฟอร์ม indicator ทั้งหมด
8. **เส้นทางเชื่อมช่องทางแจ้งเตือน:** ทดสอบปลายทางแบบผู้ใช้ยืนยัน แสดงส่งสำเร็จ/รอส่ง/ล้มเหลว และ inbox เป็นหลักฐานเสมอ ยังต้องทดสอบกับบริการจริง

## ลำดับถัดไป

แก้สถานะสิทธิ์และการติดตาม → ประวัติ/แชต/บริบทย้อนหลัง → ร่างแยกจากเวอร์ชันที่เปิด → อธิบายสัญญาณบนกราฟและควบคุมเหตุการณ์ → ทดสอบ AI/ปลายทางจริงและผู้ใช้จริง

คงประเด็นจาก audit ก่อนหน้าไว้ด้วย: preview ซับซ้อนช้า, activation ไม่ตรวจคู่จริง, replay กระโดดกลับล่าสุด และไฟล์เสียรายงานข้อผิดพลาดไม่ชัด การจำลองชุดนี้ไม่ได้แก้หรือทดสอบทุกประเด็นเหล่านั้นซ้ำ
