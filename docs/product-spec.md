# แบบประสบการณ์ผู้ใช้

สถานะ: Design v1 · 2026-10-03 · อ้างอิงการยืนยันขอบเขตใน [README](README.md)

## 1. เป้าหมาย

ผู้ใช้มีเงื่อนไขอยู่แล้วและต้องการรู้ว่า **สินทรัพย์ไหนเข้าเงื่อนไข บนกระดานไหน เมื่อไร และเพราะอะไร** โดยไม่ต้องเฝ้าหน้าจอเอง ผู้เริ่มต้นบอกแนวคิดผ่านแชตได้ แต่ snaap ต้องถามส่วนที่กำกวม ไม่แต่งสูตรและเปิดใช้งานแทนผู้ใช้

ผลสำเร็จของงานไม่ใช่การทำให้แชตตอบดูฉลาด แต่คือผู้ใช้ตรวจพบและแก้ความเข้าใจผิดก่อนเปิดแจ้งเตือน และเข้าใจได้ว่าระบบยังทำงานอยู่หรือไม่

## 2. โครงสร้างหน้าจอ

คงเมนูหลัก 4 รายการ ไม่ย้ายชื่อเมนูเองระหว่างพัฒนา

| เมนู | เนื้อหา | สิ่งที่เปิดลึกลงไปได้ |
|---|---|---|
| คุยกับ snaap | แชต ร่างเงื่อนไข ปุ่มตั้งค่าเอง | ประวัติสนทนาจริง ร่างที่ค้าง แหล่งที่มาของค่าตั้งต้น |
| รายการแจ้งเตือน | กฎที่บันทึก แท็บ “รายการ” และ “ประวัติแจ้งเตือน” | เหตุผลเข้า/ไม่เข้าเงื่อนไข กราฟประกอบ การแก้กฎ เวอร์ชัน |
| ประวัติการเทรด | นำเข้าไฟล์/เชื่อมบัญชี ตรวจความครบถ้วน ผลวิเคราะห์ | รายการผิดพลาด วิธีจับคู่ไม้ หลักฐานข้อสังเกต |
| การแจ้งเตือน | ช่องทางที่เชื่อม ทดสอบส่ง เวลาเงียบ การรวมข้อความ | สถานะการส่ง โควตา ปลายทางแต่ละรายการ |

เมนูบัญชี: โปรไฟล์ เขตเวลา กระดานที่ใช้ การเชื่อมบัญชี ข้อมูลและความเป็นส่วนตัว ส่งออก/ลบข้อมูล อุปกรณ์ที่เข้าสู่ระบบ

สถานะระบบเป็นป้ายเล็กในหน้ารายการ มีรายละเอียดเมื่อมีปัญหา ไม่เพิ่มหน้า dashboard เต็มไปด้วยตัวเลขเป็นหน้าแรก

## 3. เริ่มใช้ครั้งแรก

1. เข้าเว็บแล้วทดลองสร้าง **ร่าง** ได้ทันที มีข้อความสั้นว่า “ยังไม่ได้เปิดแจ้งเตือน”
2. ถ้าพิมพ์เงื่อนไขครบ ให้ขึ้นการ์ดสรุปเลย ไม่ถามซ้ำตาม wizard
3. ถ้าขาดข้อมูล ถามครั้งละ 1 เรื่อง เช่น “ใช้ราคา Spot หรือ Futures?” พร้อมตัวเลือกที่รองรับ
4. ขอเข้าสู่ระบบเมื่อจะบันทึกข้ามอุปกรณ์หรือเริ่มเฝ้าจริง เก็บร่างไว้ผ่านขั้นตอนเข้าสู่ระบบ
5. เลือกปลายทาง “ในเว็บ” ได้ ไม่บังคับเชื่อม Telegram เพื่อเริ่มใช้
6. ถ้าเลือก Telegram/LINE ต้องเชื่อมและทดสอบก่อนเปิดใช้ปลายทางนั้น
7. ยืนยันการ์ดสรุป → ระบบเตรียมข้อมูล → แสดงสถานะ “กำลังเฝ้า” เมื่อข้อมูลพร้อมจริง

การดูราคาสาธารณะไม่ขอ exchange API key การเชื่อมบัญชีส่วนตัวใช้เฉพาะการนำเข้าประวัติ

## 4. แชตและการตั้งเงื่อนไข

### ตัวอย่างบทสนทนา

ผู้ใช้: “หาเหรียญ USDT ใน Binance กับ Bybit ราคายืนเหนือ EMA 200 RSI ตัดขึ้น 30 วอลุ่มมากกว่าปกติ บนกราฟชั่วโมง ส่ง Telegram”

snaap: “Spot หรือ Futures?” → ผู้ใช้เลือก Spot

snaap: “วอลุ่มมากกว่าปกติ ต้องการกี่เท่าของค่าเฉลี่ย?” → เสนอ 1.5× เป็น **ค่าที่เสนอ** ให้แก้หรือเลือกได้ และอธิบายว่าเทียบ 20 แท่งก่อนหน้า

snaap: “ต้องการเลือกคู่เอง หรือสแกนกลุ่มคู่ USDT?” → การสแกนต้องระบุขอบเขต ไม่แปลว่าเฝ้าทุกคู่โดยอัตโนมัติ

การ์ดตรวจทาน:

- แหล่งราคา: Binance Spot และ Bybit Spot — ประเมินแยกกระดาน
- ขอบเขต: กลุ่มคู่ USDT ที่ผู้ใช้เลือก เกณฑ์และจำนวนคู่แสดงชัด
- กรอบเวลา: 1 ชั่วโมง · รอแท่งปิด
- เงื่อนไข: ราคา > EMA 200, RSI(14) ตัดขึ้นเหนือ 30, วอลุ่ม > 1.5× ค่าเฉลี่ย 20 แท่งก่อนหน้า
- แจ้งเตือน: Telegram ที่เชื่อมไว้ และเก็บประวัติในเว็บ
- ความถี่: เมื่อเข้าเงื่อนไขใหม่ ไม่ส่งซ้ำทุกครั้งที่ราคาอัปเดต
- ปุ่ม: “เริ่มเฝ้า”, “แก้ไข”, “บันทึกร่าง”

ค่าที่ผู้ใช้ระบุ ค่าที่ระบบเสนอ และค่าที่อนุมานจากประวัติ ต้องแยกที่มาในรายละเอียด ไม่ต้องโชว์ technical confidence score บนหน้าหลัก

### การเปลี่ยนกฎ

“เปลี่ยน RSI เป็น 35” สร้างร่างใหม่พร้อม diff `30 → 35` และคงกฎเดิมระหว่างตรวจ ถ้ากระทบหลายรายการต้องให้เลือกชื่อรายการก่อน กด “ใช้การเปลี่ยนแปลง” จึงเปลี่ยนเวอร์ชันที่กำลังทำงาน

“หยุดรายการนี้” ระบุรายการชัดแล้วทำได้ พร้อม Undo; “หยุดทั้งหมด” ต้องแสดงจำนวนรายการและปุ่มยืนยันในครั้งเดียว ไม่ถามซ้ำหลายรอบ

ห้ามนำข้อความในไฟล์ CSV ชื่อเหรียญ หรือคำตอบจากภายนอกมาเป็นคำสั่งเปลี่ยนกฎ AI สร้างได้เฉพาะร่าง ไม่มีสิทธิ์เปิดกฎ ส่งข้อความจริง หรืออ่าน secret เอง

### คนใช้สูตรละเอียด

มี editor แบบรายการเงื่อนไข รองรับ AND/OR แบบจัดกลุ่ม, > ≥ < ≤, crosses above/below, ราคา EMA SMA RSI และ volume ratio ในรุ่นแรก คำอธิบายสรุปภาษาไทยสร้างจากกฎชุดเดียวกับ evaluator

เวลาแก้ AND/OR ให้แสดงวงเล็บ/กลุ่มชัด ไม่รองรับสูตรโค้ดอิสระ, Pine Script import หรืออินดิเคเตอร์ที่ยังไม่มี implementation โดยแอบแปลงเป็นของใกล้เคียง

หลาย timeframe ออกแบบไว้: กำหนด timeframe หลักเป็นตัว trigger แล้วใช้แท่งที่ปิดแล้วล่าสุดของ timeframe อื่น ณ เวลานั้น รองรับในระยะถัดไปหลังทดสอบ temporal alignment ผ่าน

## 5. หลายกระดานและขอบเขตสแกน

ชุดกระดานตั้งต้น: Binance, Bybit, OKX, Bitget, MEXC ตามตัวเลือกเดิม ไม่อ้างว่าเป็นอันดับตลาดที่ตรวจยืนยันแล้ว สามารถเพิ่ม Kraken/Coinbase ในโครงเดียวกันเมื่อมีความต้องการ

ในรุ่นแรกหลายกระดานต้องใช้งานพร้อมกันได้ ผู้พัฒนาอาจตรวจ adapter ทีละตัว แต่ห้ามเปลี่ยน product scope กลับเป็นกระดานเดียวเงียบ ๆ

ตัวเลือกตลาด: Spot และ linear perpetual ที่ settle ด้วย USDT เฉพาะ adapter ที่ผ่านเกณฑ์รับงาน แสดงข้อจำกัดตามกระดานและภูมิภาค ไม่เลือกสัญญาอื่นแทนโดยอัตโนมัติ

ตัวเลือก “เลือกคู่เอง” ใช้ autocomplete จาก market catalogue ไม่รับคู่สะกดผิดแล้วขึ้นสถานะกำลังเฝ้า ตัวเลือก “สแกนกลุ่ม” มี quote currency, สถานะซื้อขาย, อายุการจดทะเบียน, สภาพคล่อง และรายการยกเว้น ต้องแสดงจำนวนคู่จริงก่อนยืนยัน

ค่าเริ่มต้นที่เสนอสำหรับทดสอบภาระ: กลุ่มสแกนไม่เกิน 50 คู่ต่อกระดานต่อกลุ่ม, refresh สมาชิกทุก 15 นาที, กันคู่เพิ่งเข้า/ออกวนด้วย hysteresis 2 รอบ ตัวเลขนี้เป็นข้อเสนอความจุ ไม่ใช่สิทธิ์แพ็กเกจที่เปิดขายแล้ว

กลุ่มที่เปลี่ยนสมาชิกต้องมี revision, เวลา effective และหน้า “เพิ่ม/ออกจากกลุ่ม” ผู้ใช้เลือกตรึงสมาชิกได้ ทุก signal เก็บสมาชิกและ revision ณ เวลาที่ตรวจจริง

การเฝ้าคู่เดียวกัน 2 กระดานไม่ใช่สัญญาณเดียวกัน อาจรวมหน้าตาข้อความแบบกลุ่ม แต่ต้องเก็บเหตุการณ์แยกและบอกแหล่งราคาชัด

หุ้นและทองยังอยู่ในแบบระยะถัดไป: ต้องเลือกประเทศ/session, แหล่งข้อมูลและสิทธิ์เรียลไทม์, corporate actions สำหรับหุ้น, และแยก XAUUSD/Gold Futures/ทองไทย การซื้อแพ็กเกจข้อมูลและสิทธิ์เผยแพร่ต้องตัดสินใจก่อนเชื่อมจริง ไม่มีป้าย “รองรับแล้ว” ในรุ่นคริปโต

## 6. หน้ารายการแจ้งเตือน

การ์ดแสดงชื่อ, กระดาน+ตลาด, คู่/จำนวนคู่, กรอบเวลา, สรุปกฎ, สถานะการเฝ้า, ข้อมูลล่าสุด, และปลายทาง

สถานะมี 3 แกนเพื่อไม่ทำให้เข้าใจผิด:

| แกน | สถานะที่ผู้ใช้เห็น |
|---|---|
| การใช้งาน | ร่าง / กำลังเตรียมข้อมูล / กำลังเฝ้า / หยุดชั่วคราว / เก็บถาวร |
| ข้อมูล | ปกติ / กำลังเชื่อมใหม่ / ข้อมูลล่าช้า / ข้อมูลไม่ครบ / คู่ถูกระงับ |
| ปลายทาง | พร้อมส่ง / รอส่ง / ส่งไม่สำเร็จ / ต้องเชื่อมใหม่ |

เมื่อ Bybit ขัดข้องแต่ Binance ปกติ แสดง “เฝ้าได้ 1 จาก 2 กระดาน” พร้อมเหตุผล ไม่ทำทั้งรายการเขียวหรือปิดกระดานปกติไปด้วย

กดการ์ดแล้วเปิดรายละเอียด: เงื่อนไขทีละข้อพร้อมค่าปัจจุบัน, ผ่าน/ไม่ผ่าน/ยังประเมินไม่ได้, เวลาแท่ง, แหล่งราคา, การคำนวณเวอร์ชัน, เหตุการณ์ล่าสุด, กราฟพับได้ กราฟเป็นหลักฐานเสริม ไม่แย่งหน้าที่แชต

เมื่อเปิดกฎแล้วเงื่อนไข true อยู่ก่อน: default รอเหตุการณ์เข้าใหม่ มีตัวเลือกส่ง snapshot ครั้งแรกซึ่งต้องติดป้าย “เข้าเงื่อนไขอยู่แล้วตอนเปิดใช้” ให้ชัด

กดหยุด → หยุดการประเมินและงานส่งที่ยังไม่เริ่มของรายการนั้น ข้อความที่ provider รับไปแล้วเรียกคืนไม่ได้ การเริ่มใหม่ต้องเติมข้อมูลก่อนจึงเปลี่ยนเป็นกำลังเฝ้า

## 7. การแจ้งเตือนและความเชื่อถือได้

ทุกสัญญาณถูกเก็บใน inbox ในเว็บ แม้ไม่ได้เปิดเว็บอยู่; การเห็นทันทีขึ้นกับ runtime ที่กำลังทำงาน การปิดแค่แท็บไม่ควรหยุด backend แต่ **ปิดเครื่องหรือเครื่อง sleep ในโหมด local จะหยุดเฝ้า** หลังกลับมาต้องแสดงช่วงขาด ไม่อ้างว่า 24/7

ข้อความหนึ่งรายการประกอบด้วย: ชื่อกฎ, คู่, กระดานและตลาด, กรอบเวลา, เวลาเข้าเงื่อนไขตามเขตเวลาผู้ใช้, ค่า indicator ที่ผ่านจริง, ระหว่างแท่งหรือแท่งปิด, ลิงก์ดูรายละเอียด ไม่มีคำสั่งซื้อ/ขายแทนผู้ใช้

### การเชื่อมช่องทาง

- Telegram: “เชื่อม Telegram” → เปิดบอตพร้อมรหัสใช้ครั้งเดียว → ผู้ใช้กด Start → snaap แสดงผู้รับที่ mask แล้ว → “ส่งทดสอบ” → ผู้ใช้ยืนยันว่าได้รับ ไม่ต้องวาง bot token ในแชต
- Local เริ่มจากบอตของเจ้าของติดตั้ง: เก็บ token ฝั่ง server ผู้ใช้ปลายทางแค่เชื่อมกับบอตนั้น การใช้งานหลายบัญชีในอนาคตต้องมี identity binding
- LINE: เชื่อมผ่าน Messaging API/บัญชี OA, ผูก LINE user กับ snaap ด้วย flow ที่ตรวจตัวตนและ nonce ไม่รับ LINE user ID ที่กรอกเองแล้วเชื่อว่าเป็นเจ้าของ บริการ LINE Notify ยุติแล้ว [R09](research.md)
- Webhook: สำหรับผู้ใช้ขั้นสูง กำหนด HTTPS URL, secret, ส่งทดสอบและดูผลตอบกลับได้ มีข้อจำกัด SSRF ใน [architecture](architecture.md)
- ช่องทางในเว็บมีเสมอ คำว่า “ผู้ให้บริการรับแล้ว” ไม่เท่ากับ “อ่านแล้ว” หากไม่มีหลักฐานการอ่านจริง

### ควบคุมจำนวนข้อความ

เลือกเฉพาะรายการ, เงียบชั่วคราว, เวลางดรบกวนตาม IANA timezone, ส่งทันทีหรือ digest ผู้ใช้เห็นผลว่าการเงียบยังเก็บ inbox แต่ไม่ส่ง push และไม่ส่งย้อนหลังรัว ๆ ตอนหมดเวลาเงียบ

ถ้าหลายคู่เข้าเงื่อนไขในแท่งเดียว รวมข้อความตามกฎ+กระดานได้ แต่เปิดดูรายคู่ได้ ปุ่ม “ซ้ำเกินไป” เสนอ cooldown/digest ให้ตรวจ ไม่แก้เงื่อนไขเทรดเอง

### สถานะการส่ง

รอส่ง → กำลังส่ง → ผู้ให้บริการรับแล้ว / ลองใหม่ / ไม่ทราบผล / ส่งไม่สำเร็จ / หมดอายุ / งดส่ง

network timeout หลังส่งออกอาจไม่ทราบว่าปลายทางรับแล้วหรือไม่ ต้องแสดง “ไม่ทราบผล” ไม่แปลงเป็น fail แล้วส่งซ้ำไม่จำกัด หาก provider ไม่มี idempotency ห้ามสัญญาว่าจะไม่มีข้อความซ้ำ 100%

## 8. ประวัติการเทรดและการค้นหารูปแบบ

สองทาง: CSV/XLSX สำหรับประวัติเก่าหรือทดลองก่อนเชื่อม; API แบบอ่านอย่างเดียวสำหรับซิงก์ต่อเนื่อง ทั้งสองนำเข้าผ่าน pipeline เดียวกันและตรวจซ้ำข้ามแหล่งได้

ขั้นตอน: เลือกแหล่ง → ตรวจรูปแบบ/เขตเวลา → แสดง preview → รายงานช่วงข้อมูล/แถวซ้ำ/ค่าธรรมเนียมขาด → ยืนยันนำเข้า → ประมวลผล → ตรวจผล

หน้าจอไม่ขึ้น “สำเร็จ” ถ้ารับไฟล์แล้วแต่ยังวิเคราะห์ไม่เสร็จ แยก รับไฟล์แล้ว/กำลังอ่าน/รอตรวจคอลัมน์/กำลังประมวลผล/เสร็จบางส่วน/เสร็จ/ล้มเหลว และแก้เฉพาะแถวที่มีปัญหาได้

รองรับ partial fills, ทยอยเข้า–ออก, fee หลายสกุล, funding, สัญญา long/short, hedge mode และ opening balance ที่ไม่ทราบ ถ้าจับคู่ไม่ได้ต้องให้ตรวจ ไม่แต่ง entry ย้อนหลัง ข้อมูลไม่ครบต้องแยกออกจากสถิติที่ต้องใช้ข้อมูลครบ

รายงานมีทั้งกำไรและขาดทุน แยก P&L ที่กระดานรายงานกับที่ snaap คำนวณ มีค่าใช้จ่ายที่รวม/ขาดและวิธีตีราคาค่าธรรมเนียม ผู้ใช้เลือก grouping ได้แล้วเก็บเวอร์ชันการวิเคราะห์

ข้อสังเกตเช่น “รายการที่เลือกมักเกิดหลัง RSI ฟื้นตัว” ต้องมีตัวอย่างอ้างอิง จำนวนตัวอย่าง ช่วงวันที่ coverage และ counterexamples ไม่สรุปว่าเป็นสไตล์ของผู้ใช้จากไม้ที่กำไรอย่างเดียว

แยก 3 อย่าง: **สิ่งที่ผู้ใช้บอกว่าเป็นสไตล์**, **พฤติกรรมที่พบ**, **สมมติฐานสำหรับทดลอง** ผู้ใช้กด “ตรงกับฉัน / ไม่ใช่ / ไม่นับรายการนี้” ได้โดยไม่แก้ประวัติดิบ

ใช้ข้อมูลตลาดก่อนเวลาที่เข้าเทรดเท่านั้น หากประวัติมีเวลาไม่ละเอียดพอหรือ candle ตรงช่วงขาด ให้รายงาน unknown ข้อสังเกตที่ใช้ข้อมูลขาดไม่ผ่านไปเป็นกฎอัตโนมัติ

“สร้างเงื่อนไขจากผลนี้” เปิดร่างและหลักฐาน ไม่เปิดเฝ้าทันที ก่อนบอกว่ามีประสิทธิภาพต้องมี chronological holdout, ค่าใช้จ่าย, จำนวนตัวอย่าง และทดสอบ out-of-sample แบบที่ไม่เลือกช่วงเพื่อให้ดูดี

## 10. ข้อมูลและการควบคุมของผู้ใช้

ส่งออกกฎ+history+alert log ได้ ยกเลิกการเชื่อมต่อแต่ละแหล่งได้ แยก “ลบไฟล์ต้นฉบับ” “ลบข้อมูลนำเข้า” “ลบบัญชี” ให้เข้าใจผล การลบ history ที่เป็นหลักฐานข้อสังเกตต้อง invalidate ผลที่อ้างอิงด้วย

ก่อนใช้ AI กับข้อมูลประวัติ แจ้งว่าจะส่งข้อมูลประเภทใดให้ผู้ให้บริการใด ใช้สรุปที่ตัดตัวระบุ/ยอดเงินไม่จำเป็น ไม่ส่ง API key การเปิด local ไม่ได้แปลว่า AI และ API ภายนอกจะทำงาน offline

## 11. มาตรฐานประสบการณ์

- คีย์บอร์ดทำทุกขั้นตอนได้ focus เห็นชัด dialog กลับ focus ถูกจุด และไม่ใช้สีอย่างเดียวบอกสถานะ
- เกณฑ์ข้อความปกติ WCAG AA อย่างน้อย 4.5:1; ตัวเลขคอนทราสต์ไม่ใช้แทนการดูขนาด/น้ำหนักจริง
- อ่านไทยบนจอ 390px และซูม 200%; ไม่มีเมนูเปลี่ยนความสูงเมื่อ active; ข้อความสำคัญไม่ถูก ellipsis จนเสียความหมาย
- เวลาจัดเก็บเป็น UTC แสดงตาม timezone ผู้ใช้ แต่ขอบแท่งตาม source/session ห้ามเลื่อนแท่งตาม timezone หน้าเว็บ
- ข้อความ loading บอกงานจริง มี retry/cancel เมื่อเหมาะสม ไม่เพิ่มการ์ดตกแต่งหรือคำปลอบยาว ๆ
- เป้าหมาย usability สำหรับทดสอบ: มือใหม่สร้างร่างถูกต้อง 1 รายการได้ใน 3 นาทีโดยไม่ต้องรู้ชื่อ API; เป็นเป้าหมาย ยังไม่ได้วัด
